# 微信虚拟支付改造原始业务需求

## 1. 文档定位

- 本文档只整理微信虚拟支付改造的原始业务需求。
- 本文档不包含数据库表结构、状态机、锁、限流、重试策略或其他技术方案。
- 后续技术方案以本文档最终确认的业务需求为输入，重新独立设计。

## 2. 改造目标

1. 将现有“普通微信支付充值积分”改为“微信小程序虚拟支付代币”。
2. 用户在 WeFolio 中看到和使用的仍称为“积分”。
3. 现有积分消费场景、计费规则和积分数量原则上保持不变，只替换积分余额来源和微信结算方式。
4. 微信侧代币余额是微信余额的最终依据，本地不能自行增加微信余额。

## 3. 余额组成

系统需要识别以下数值：

- 微信总代币余额；
- 微信赠送代币余额；
- 微信有价充值代币余额；
- 已消费但尚未从微信扣除的代币，简称“待扣代币”；
- 已获得但尚未赠送到微信的代币，简称“待赠代币”；
- 用户实际可用积分。

计算规则：

```text
实际可用积分
= 微信总代币余额
- 待扣代币
+ 待赠代币
```

如果微信区分有价充值代币和赠送代币，本地也需要对齐展示：

```text
微信有价充值代币
= 微信总代币余额 - 微信赠送代币余额
```

实际可用积分允许为负数，不得截断为 0。

## 4. 积分消费

1. 用户发生积分消费时，业务消费是一笔完整金额，不是部分消费。
2. 消费前实际可用积分大于 0，允许执行本次完整消费。
3. 本次消费允许把实际可用积分从正数降到 0 或负数。
4. 消费后实际可用积分小于或等于 0，后续收费功能按照原有“余额为 0”的逻辑限制。
5. 实际可用积分小于或等于 0 后，不再产生新的用户消费或后台自动消费。
6. 已经形成的待扣代币仍需要在后续条件满足时从微信结算，不能因为用户进入负数而丢失。
7. 原始需求没有要求把一笔业务消费拆成多次部分扣除。

## 5. 微信扣币和 `session_key`

### 5.1 `session_key` 有效

1. 先完成本地业务消费。
2. 随后立即调用微信扣币。
3. 微信扣币成功后，待扣代币相应减少。
4. 微信扣币结算不能再次减少用户的实际可用积分，因为消费发生时已经扣过一次。

### 5.2 `session_key` 无效或不存在

1. 本地业务消费仍然成立。
2. 消费金额进入待扣代币。
3. 如果用户当前在线，小程序静默调用 `wx.login`。
4. 后端使用新的登录 code 刷新 `session_key`。
5. 刷新成功后再次尝试结算待扣代币。
6. 刷新失败时保留待扣，不回滚已经成功的业务。
7. 长期未登录用户无法主动刷新会话，待扣保留到用户下次登录。

## 6. 积分赠送

### 6.1 当前全部赠送场景

当前赠送积分只有以下五类场景，不存在“其他”赠送场景：

1. 新用户首次登录并完成注册后的赠送；
2. 新用户注册时使用有效推荐码后，向推荐人赠送；
3. 充值套餐中 `bonusPoints` 对应的赠送；
4. 后台人工赠送积分；
5. 历史测试用户迁移时的一次性赠送。

### 6.2 通用赠送规则

1. 以上五类场景都属于赠送，统一改用微信虚拟支付的赠送代币能力。
2. 赠送业务成立时立即形成待赠代币。
3. 待赠代币立即计入实际可用积分。
4. `session_key` 有效时，立即调用微信赠送代币。
5. `session_key` 无效时保留待赠，静默刷新或下次登录后再赠送。
6. 微信赠送成功后，微信余额增加、待赠减少，实际可用积分不能重复增加。
7. 同时存在待赠和待扣时，先完成待赠，再处理待扣。
8. 赠送金额继续使用各业务已有配置，不额外增加重复配置。

### 6.3 新用户赠送

1. 新用户首次创建时，微信代币余额视为 0。
2. 新用户首次登录并完成注册后赠送 1000 积分。
3. 金额继续使用现有新用户赠送配置，当前为 1000。
4. 新用户本地先形成待赠 1000。
5. 有有效 `session_key` 时立即向微信赠送。
6. 不新增另一套“虚拟支付新用户赠送金额”配置。

### 6.4 推荐人赠送

1. 新用户注册时填写有效推荐码后，向推荐人赠送积分，不向新用户重复赠送推荐积分。
2. 推荐人继续获赠 500 积分。
3. 金额继续使用现有推荐人赠送配置，当前为 500。
4. 推荐码为空、无效或指向新用户本人时，不产生推荐人赠送。
5. 新用户本人的注册赠送仍按 6.3 节独立处理。

### 6.5 充值套餐赠送

1. 充值套餐中的基础积分属于用户购买的有价充值代币，不属于赠送。
2. 充值套餐中的 `bonusPoints` 属于赠送，充值支付成功后按赠送代币处理。
3. 当前 1 元档和 10 元档的 `bonusPoints` 均为 0，不产生赠送。
4. 当前 50 元档赠送 20 积分，100 元档赠送 100 积分。
5. 充值赠送金额继续使用充值套餐已有的 `bonusPoints` 配置，不新增另一套虚拟支付赠送配置。
6. 充值赠送形成待赠后，按 6.2 节的通用赠送规则处理。

### 6.6 后台人工赠送

1. 后台人工赠送积分接口产生的积分全部属于赠送。
2. 赠送金额以本次后台人工赠送请求为准。
3. 后台人工赠送形成待赠后，按 6.2 节的通用赠送规则处理。

### 6.7 历史测试用户迁移赠送

1. 当前历史用户全部是测试用户。
2. 当前历史用户微信代币余额都是 0。
3. 清空历史测试用户原有的消费记录和充值记录。
4. 不保留历史本地积分余额。
5. 每个历史用户初始化为待赠 500、实际可用积分 500。
6. 历史用户初始化金额复用迁移执行时的新用户赠送配置，当时为 500。
7. 不新增历史用户专用赠送金额变量。
8. 历史用户目前没有持久化的有效 `session_key`，迁移时不调用微信。
9. 历史用户下次登录取得有效 `session_key` 后，再向微信赠送这 500 代币。
10. 微信赠送成功后，微信赠送余额变为 500、待赠变为 0，实际可用积分仍为 500。

## 7. 充值

1. 用户通过 `wx.requestVirtualPayment` 购买微信有价充值代币。
2. 充值套餐的基础积分对应有价充值代币，套餐赠送积分按 6.5 节单独作为赠送处理。
3. 充值完成后，以微信返回的余额为准。
4. 充值成功后刷新微信总代币余额和赠送代币余额。
5. 如果用户存在待赠，先按赠送规则处理；如果用户存在待扣，随后继续尝试结算。
6. 充值后实际可用积分仍按统一公式计算。
7. 现有普通微信支付充值入口最终下线。

## 8. 页面展示

积分概览需要展示真实的实际可用积分，包括负数。

积分详情至少展示：

- 实际可用积分；
- 微信总代币余额；
- 微信有价充值代币余额；
- 微信赠送代币余额；
- 待扣代币；
- 待赠代币。

用户需要能查看待扣和待赠的业务来源及金额，但原始需求没有要求展示每一次微信调用尝试。

## 9. 欠费和功能限制

1. 实际可用积分小于 0 表示欠费。
2. 实际可用积分等于 0 和小于 0 使用相同的功能限制。
3. 限制范围直接复用现有“积分余额为 0”的业务规则。
4. 用户仍需能够登录、查看积分详情和充值。
5. 充值或赠送使实际可用积分重新大于 0 后，恢复相关功能。

## 10. 数据留存的简化要求

1. 待扣只需要保存当前结算情况和最后一次失败原因。
2. 待赠同样只保存当前结算情况和最后一次失败原因。
3. 不要求保存每一次微信调用尝试。
4. 最终成功后，该笔赠送或扣除结果不再被后续重试修改。
5. 不因为审计、监控或未来扩展提前引入当前业务不需要的复杂模型。

## 11. 不属于原始业务需求的内容

以下内容来自此前的技术设计讨论，不应直接视为业务要求：

- 部分补扣；
- 每次调用一条尝试记录；
- 复杂的尝试状态机；
- 多笔部分扣除订单及其排序；
- 钱包租约的具体秒数；
- HMAC 表结构；
- 数据库防重放表；
- Redis 或 JVM 锁的具体实现；
- QPS、并发数及告警阈值；
- 分阶段上线的具体数量和步骤；
- 自动退款和复杂冲正流程；
- 为未来多实例提前设计的存储模型。

## 12. 待明确的业务边界

以下内容需要在重新设计前逐项确认：

1. 微信余额不足整笔待扣金额时，是等待余额足够，还是允许部分扣除。
2. 已经成功扣除微信代币后，业务是否存在退款需求。
3. “清空历史消费记录和充值记录”是否还包括月度账单、积分计量等关联测试数据。
4. 微信调用明确失败后，是自动重试，还是只在登录、充值等事件发生时再次处理。
